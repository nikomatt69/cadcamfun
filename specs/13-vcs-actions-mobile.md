## 1. Decisions

### Expo migration refinement (2026-10-11)

WP13 now owns the existing React Native/Expo Router migration in `apps/mobile`. Refine that app rather than restore the removed Tauri shell. Cross-WP integration includes the companion test imports and scoped gateway question/session-state routes in WP4, and Expo build/simulator workflows in WP0. The phone retains certificate-pinned HTTPS, scoped tokens in secure storage, and the same server-owned CAD/CAM assistant. The local `CompanionNet` Expo module requires a native development build: Expo Go can render an explanatory setup screen but cannot connect through an unpinned fallback. Startup, reconnect, request cancellation, SSE completion/recovery, native module loading, deep-link pairing, configuration and CI must agree with this runtime.

Commands from `apps/mobile`: `bun run ios` builds/installs the native app and starts Metro; `bun run ios:build` builds without Metro; `bun run ios:dev` starts Metro for an installed development build on localhost; `bun dev` starts Metro for the development client. `expo dev` is not an Expo CLI command. iOS simulator verification and signed device/TestFlight release are separate outcomes.

1. **Every CADCAMFUN project is a git repository.** History, branches, tags, diffs, pull requests and CI are all built on git's object model, not on the old `*Version` snapshot tables (which stay for the legacy routes).
2. **Git is the source of truth, SQLite is the working copy.** The database holds the checked-out state of the project; `commit` snapshots it into the repository, `checkout`/`merge`/`restore` write a tree back into it. A dirty working copy (database ≠ HEAD) blocks checkout, merge and restore, exactly like `git`.
3. **Byte-compatible with git.** Blobs, trees and commits use git's loose-object format and SHA-1, so an oid is identical here, in a `git clone`, and on GitHub. This is verified against the real `git` binary in `packages/vcs/test`. Consequence: the GitHub mirror needs no mapping tables.
4. **Collaboration is internal; GitHub is an optional mirror.** Users and organisations collaborate inside CADCAMFUN: access follows `Project` ownership / `UserOrganization` roles (members read, commit to branches, open and review pull requests; the owner or an org ADMIN/MANAGER moves shared branches and merges). `GitRepo.remote` (`owner/repo`) links a project to a GitHub repository that is synchronised with `push` / `pull`.
5. **Workflows look like GitHub Actions but cannot run code.** `uses:` names a registered CADCAMFUN step; there is no `run:` shell and no Docker. A workflow naming an unregistered step fails before any step runs.
6. **The phone is a companion, not a second app database.** iOS cannot spawn the Bun sidecar, so the phone is a thin client of a desktop that owns the data. The AI assistant on the phone works through the same tools as on the desktop and edits the checked-out branch, including `main`; `ai/*` branches and pull requests are optional when requested for review, and a person merges.

## 2. Repository layout (what is committed)

### Local Git identity and repository bootstrap (2026-10-17)

Owner-requested cross-WP scope: WP0 `GitProfile` schema/migration; WP3 authenticated user endpoints and generated clients; WP4 VCS repository/service, project creation and startup wiring; WP6 Settings → Profile identity card; WP8 VCS prompts and generated harness inventory. Each user has one database-backed Git identity (`userId` primary key and cascading foreign key to `User`, `name`, `email`, timestamps). Missing identities are seeded from account fields at startup or first use. Editing the Git identity changes future commit attribution only; it does not change the account or rewrite history. AI authors use the same identity with ` (AI)` appended to the name.

`GET /api/user/git-profile` reads or creates the current user's identity (401/404/500). `PUT` accepts `{ name, email }`, trims both fields, rejects invalid Git identifiers (400), and only changes the authenticated user's identity. Settings → Profile loads, edits and saves these fields with visible loading/error/retry feedback.

New projects receive an `Initial commit` on `main`; startup backfills existing projects without history without changing established branches. AI edits, commits and restores may use the checked-out branch, including `main`; `ai/*` and pull requests are optional review flows. AI merges into `main` remain blocked. Read-only VCS tools must not initialize or commit a repository. The fallback for a first AI commit must record the requested work once and return its commit rather than fail with `nothing-to-commit` after initializing it.

```
project.json                    name, description, isPublic
drawings/<id>.json              one file per entity => diffs and merges stay local
components/<id>.json
toolpaths/<id>.json             includes the generated G-code
materials/<id>.json             library items the project's toolpaths use (material, tool, machine)
tools/<id>.json
machine-configs/<id>.json
costs/<id>.json                 production cost estimates of the toolpaths
.cadcamfun/workflows/<n>.yml    workflows, versioned with the model
```

**What is tracked, and why.** Everything that is part of a project's manufacturing state is in the tree: the project itself, its drawings, components and toolpaths (with G-code), the materials, tools and machine configurations those toolpaths reference, and their cost estimates. Library items are shared across projects, so applying a commit creates the ones that are missing and updates an existing one only when the current user owns it; owners and organisations are installation-specific and are not stored. Not tracked, on purpose: thumbnails (derived), comments and chat (conversation, not model state), uploaded binaries and per-user cost settings. Every history-changing action (commit, checkout, restore, pull-request open/merge) is also appended to the legacy `ActivityLog`, so it shows up in the same audit trail as every other change.

**History of one item.** `GET …/vcs/log?path=drawings/<id>.json` lists only the commits that touched that file, and `POST …/vcs/restore` with `paths` puts only those files back to an older version as a new commit, leaving the rest of the project as it is. The desktop exposes both from each drawing/component/toolpath card (History button) and from the project's Version control screen.

Canonical JSON (sorted keys, 2 spaces) keeps text diffs stable. Thumbnails are derived data and are not committed. `.json` files merge **structurally** (`mergeJson`): two people editing different properties of one drawing do not conflict; same property, or arrays, report a conflict with JSON pointers.

### Step registry

A step is a pure function of the commit being checked (`ctx.files`) and its own `with:` parameters, never of the live database, so a run always reports on the tree that was pushed. `ctx` also carries `actor` — the account that dispatched the run — so a step that writes is attributed to whoever asked for it, not to the local profile.

Steps split in two, because the runner cannot depend on a service built above it:

- **Pure** (`apps/sidecar/src/services/workflow-steps.ts`, available to every layer that builds the runner): `project/validate`, `project/require-gcode`, `cam/verify`, `cam/gcode`.
- **Service-backed** (added through `WorkflowRunner.register`): `vcs/commit` and `notify/push`, registered by `workflow-service-steps-live.ts`, which owns `ProjectVcs` and `NotificationService`; `ai/prompt`, registered by `AiLive`.

| Step | `with:` | Fails on |
| --- | --- | --- |
| `project/validate` | — | an entity file that is not JSON, an `id` not matching the file name, a missing `name` |
| `project/require-gcode` | — | a toolpath in the commit with no G-code |
| `cam/verify` | `toolpath?`, `tolerance?`, `severity?` (`error` \| `warning`) | any `error` from the replay — rapid in material, gouge, uncut stock, shank/holder/fixture collision, below stock — plus warnings when `severity: warning` |
| `cam/gcode` | `toolpath?` | the committed G-code differs from what its stored generation request produces (a stale export) |
| `vcs/commit` | `message`, `files?` (`.cadcamfun/**` text files only) | a dirty working copy, a path outside `.cadcamfun/`, or an AI actor on `main` |
| `notify/push` | `title?`, `body?`, `outcome?` (`success` \| `failure`) | never: best-effort, writes a `WORKFLOW_PASSED` / `WORKFLOW_FAILED` row |
| `ai/prompt` | `prompt` (may embed `${{ files.<path> }}`), `system?`, `model?` | the model is unreachable or errors; the answer comes back as `outputs.text` |

`cam/verify` and `cam/gcode` read the generator request stored on each toolpath, so a run that uses them needs the toolpaths to have been generated. A toolpath that *cannot* be verified — a lathe job, no stored request — is listed in `skipped` and never counted as verified: an unverifiable toolpath is not a verified one. A workflow naming an unregistered step fails before any step runs; `ai/prompt` stays unregistered until the AI layer is up, which is why the registry test asserts its absence.

`WorkflowRunner.trigger(projectId, ref, event, { onEvent?, actor? })` takes the actor in an options object (it replaced a positional callback). `WorkflowRunner.steps()` lists what a workflow may name, for the workflow editor and for error messages.

Workflow example:

```yaml
name: Validate
on:
  push: { branches: [main, "ai/**"], paths: ["toolpaths/**"] }
  pullRequest: { branches: [main] }
  manual: {}
jobs:
  check:
    steps:
      - id: v
        uses: project/validate
      - uses: project/require-gcode
```

Registered steps (see §3): `project/validate`, `project/require-gcode`, `cam/verify`, `cam/gcode`, `vcs/commit`, `notify/push`, `ai/prompt`.

### Mobile assistant transport: nikcli mobile architecture (2026-10-17)

Owner decision: the phone assistant follows `/Volumes/SSD/Projects/nikcli/packages/mobile` (`use-session-stream.ts`) in architecture, on CADCAMFUN contracts. Sending and receiving are separate:

- `POST /api/ai/sessions/prompt` (body = `StreamChatBody`) starts the turn on the desktop and answers `{ sessionId }` as soon as the host session exists (the turn's `turn/start` event); the turn then runs in the sidecar, owned by no HTTP request. A disconnected, suspended or killed phone never stops or replays it; only `chat/abort` (Stop) does.
- `GET /api/ai/sessions/:sessionId/stream?after=<seq>` is a long-lived per-session SSE stream. Each frame is `server.connected` (first frame of every connection: `seq`, `busy`), `server.heartbeat` (every 15 s), or `event` (`seq`, the `AiStreamEvent`). The sidecar keeps a bounded per-session journal (`seq` strictly increasing), so `after` replays exactly what the phone missed; if the journal no longer covers `after`, `server.connected.reset` tells the client to re-read `sessions/state` instead of resuming.
- The phone keeps one stream per open conversation, reconnects with backoff, and treats a second `server.connected` as a reconnection (nikcli `onReconnect`): it re-reads state. The POST is never retried after an uncertain delivery.
- Ownership: both routes use the same session-owner and project checks as `chat/stream`; the gateway allow-lists both. `chat/stream` stays for the desktop and older phones.
- **Busy sessions (2026-10-17).** A prompt naming a session that already has a turn running on this desktop answers **409 Conflict** (nikcli answers `SessionBusyError` 409 the same way); the running turn is untouched, and the phone steers it with `chat/queue` or stops it. A 409 certainly started nothing, so the outbox may keep the message and send it after `done`. The check and the claim are one synchronous step, so two racing prompts cannot both start. A prompt the host refuses before it starts (unknown model, wrong owner) answers 400 with the host's reason and never enters the session's journal.
- **Journal bounds.** Per session: 4 000 events and ~2 M characters of encoded JSON (the newest event always stays); overall ~24 M characters, idle sessions dropped first (least recently active), then a running one's oldest history; 64 sessions, idle ones evicted first; an idle session expires after 30 minutes. Whatever a bound drops is answered with `reset`, never skipped silently. A reset greeting replays nothing and its `seq` is the live edge (the phone re-reads `sessions/state`).
- **Restarts.** Sequence numbers start at the clock (epoch ms) of the sidecar process, so they keep increasing across restarts: a cursor from an earlier process, or one from the future, is a `reset` at the live edge, and the new turn's events still reach the follower (before, a stale high cursor silently filtered them out).
- **Followers.** The live bus is a sliding buffer (2 048 events): a phone that stops reading cannot grow memory. Every journal entry links to the previous one of its session (`prev`), so a follower that fell behind notices the gap and replays the missing entries from the journal in order; if the journal no longer has them it sends a second `server.connected` with `reset` (the phone already treats a second greeting as a reconnection). Heartbeats every 15 s (the phone's stale watchdog is 40 s); the stream never times out at the gateway.
- **A cut turn.** A turn whose fiber ends without the host's `done`/`error` (a failure inside the stream, an interruption) records a final `error` event (`code: "internal"`), so a follower is never left waiting on a turn that is over. Failures are logged, not swallowed.
- **Conversation list and history (nikcli mobile `session.list` / `session.detail`).** `GET /api/ai/sessions?projectId=&limit=` (1–100, default 50) lists the conversations the caller owns in that project, newest first: `[{ id, projectId, title, createdAt, updatedAt, busy }]` (ISO times or null; `busy` = a turn this desktop started is running; titles and times from the host, ownership from the owner records; child/worker sessions and sessions the host no longer has are not listed; without a host every owned session is listed as "Conversation"). `GET /api/ai/sessions/:sessionId/messages?before=&limit=` (1–100, default 30) pages one conversation, oldest first: `{ sessionId, messages: [{ id, role: "user"|"assistant", text, createdAt, agent, model, error, truncated, tools: [{ callId, tool, status: "pending"|"running"|"completed"|"error", input?, output, truncated }] }], before }` — pass `before` back for older messages, null on the first page. Compaction summaries and synthetic continuation turns are hidden; reasoning is not carried. Bounds: 32 000 characters of text per message, 8 000 per tool output, tool arguments over 4 000 characters left out (`truncated`), at most the newest 2 000 host messages are reachable. An unknown session, someone else's, or a `before` that is not in the conversation is a 400 (as `sessions/state`); both routes are GET-only on the gateway.

### Mobile assistant reliability (2026-10-17)

Owner-requested integration scope: WP13 owns the mobile transport, assistant lifecycle and reconnect presentation; WP8 owns interruption handling in the existing nikcli chat adapter; WP4 owns companion end-to-end regression fixtures. No new wire format or gateway privileges are required. A host interruption returned as a prompt result follows the same recovery rules as a rejected prompt. Stored completed answers are recovered before considering a retry; confirmed tool execution must never be replayed by resending the user's mutation. Switching mobile projects or reconnecting detaches the stream without stopping desktop work. Only the Stop action aborts the server turn. Reconnect restores stored tool results and pending permissions/questions through the existing scoped state/control endpoints. An uncertain delivery is never automatically queued for execution again.

1. Phone: *"make the plate 20 mm wider and regenerate the pocket"* → `POST /api/ai/chat/stream` on the paired desktop.
2. Assistant (tools in `apps/sidecar/src/services/ai-vcs-tools.ts`): `vcs_status` → `vcs_start_change` (creates and checks out `ai/<topic>`; refuses on a dirty working copy) → `cad_*` / `cam_*` edits → `vcs_commit` → `vcs_open_pull_request` (+ `actions_run`).
3. Pull request opens → `pullRequest` workflows run (validation, G-code present, later `cam/verify`).
4. Phone shows the PR (entity/property diff, workflow status); the person approves and merges, or asks for changes in chat.
5. After the merge the desktop working copy is updated (when `main` is checked out) and, if a remote is set, `push` mirrors it to GitHub.

## 6. Transport and the iOS app

The sidecar listens on `127.0.0.1` only. A phone reaches it through the **companion gateway** (`apps/sidecar/src/services/companion*.ts`, built and tested end to end against a real sidecar process):

- Opt-in: Settings → Mobile companion (`/settings/companion`) turns it on and shows the pairing QR; off by default and re-enabled automatically after a restart only if it was on.
- Separate HTTPS listener (`0.0.0.0`, default port 8443) with a per-install self-signed P-256 certificate stored under `<dataDir>/companion/` (key `0600`). The QR carries the certificate's SHA-256 fingerprint; the phone pins it (no trust-on-first-use, no HTTP).
- **Scoped, revocable device tokens** (32 random bytes, only their SHA-256 is stored, compared in constant time; shown once, inside the QR). The gateway swaps in the sidecar's real bearer token when forwarding, so the phone never holds it.
- Route allow-list (`COMPANION_ROUTES`): `GET /api/health`, `GET /api/projects`, `/api/projects/:id/(vcs|pulls|actions)/**`, `GET /api/projects/:id/workspace/**`, `GET /api/ai/status|models|agents`, `POST /api/ai/chat/stream|chat/abort|chat/queue|permission/reply|sessions/control|sessions/state|sessions/prompt`, `GET /api/ai/providers`, `GET /api/ai/sessions`, `GET /api/ai/sessions/:id/stream|messages`, `GET /api/notifications`, `POST /api/notifications/mark-all-read`, `PUT|DELETE /api/notifications/:id`, `GET /api/projects/:id/events`. The read-only agent roster lets the phone select the same CADCAMFUN specialist as the desktop without exposing host configuration or credentials. Everything else (credentials, plugins, files, billing, `/api/companion`, the raw drawing/component/toolpath document routes…) answers 403. 10 failed authentications per minute from one address → 429.
- **Workspace preview (GET only).** `GET /api/projects/:id/workspace/drawings|components|toolpaths` returns summaries (id, name, subtitle, updatedAt) and never the stored `data` document. `…/drawings/:drawingId/preview` and `…/components/:componentId/preview` return a bounded triangle mesh (`positions`, `indices`, `normals`, per-element `parts`, `truncated`, `revision`) computed on the desktop with `elementMesh`. `…/toolpaths/:toolpathId` returns the G-code text and move stats. `…/toolpaths/:toolpathId/preview` returns coloured segments (`rapid` / `linear` / `circular`) whose `line` is the 1-based G-code row, plus the stock box. `…/library` lists the project's components and the materials, tools and machines its toolpaths reference. Caps are 80 000 triangles and 20 000 segments. POST, PUT and DELETE on these paths answer 403 at the gateway. Defining a component is an assistant prompt on the checked-out branch (optionally `ai/*` for review); the phone does not PUT geometry. The phone draws the payload with the local Expo module `modules/preview` (Metal). Camera, picking and G-code sync stay in JavaScript. Before anything reaches the GPU, the phone applies the same caps and refuses a payload that is non-finite, the wrong shape, or indexed outside its vertices. A toolpath playhead is a second, tiny upload so scrubbing does not reallocate the path.
- **Conditional previews (2026-10-17).** The drawing/component mesh, the toolpath review and the toolpath path carry a strong `ETag` (SHA-256 of payload format, route, entity, revision and stored content, so two edits in one millisecond or a checkout of an older snapshot still change it) and `Cache-Control: private, no-cache`. `If-None-Match` with that tag answers **304** with no body before anything is tessellated; project and entity access are checked first (a foreign route is still 404). Encoded payloads are kept in a bounded LRU (48 entries, 64 MiB; an entry larger than the budget is served, never kept). Mesh coordinates and normals travel rounded to 1e-5 (below float32 spacing above 64 mm), which roughly halves the JSON. An element the kernel cannot mesh, or meshes to non-finite values, is listed with zero triangles instead of failing the preview or making the phone refuse the payload; non-finite G-code points are dropped. A program-only toolpath preview expands arcs into chords of at most 1 mm along their centre (helical Z interpolated), the same curve as the G-code path; every chord of one arc shares its move's `line`.
- **Machine-aware toolpath preview (2026-10-18).** The toolpath path preview is payload format 3: `…/toolpaths/:toolpathId/preview` may carry a `machine` block beside segments and stock. It holds the kind (`mill` / `lathe` / `3dprinter`), how the machine was resolved (`source`, optional `mismatch`), axes, turns, workholding, assumptions, the lathe `xMode` / `turret`, the bodies in display coordinates (`box`, `cylinder-x`, `cone-x`; `spins` for the parts that turn, `assumed` for a workholding the desktop had to assume, `wire` for the mill stock outline and the printer build volume), `spin` runs as signed display revolutions per second from a segment on, the indices of the `collisions` segments, and the `tool` glyph (`family`, diameter, width, nose radius, insert, turret). The sidecar builds it with core's `machineScenePreview` from the stored CAM document, its kernel artifact or G-code, the settings/stock and the referenced tool row; the display mapping stays desktop-side, so the phone never imports the CAD kernel. The phone tessellates each body (at most 20 000 triangles per static / spindle set), draws opaque bodies with depth write and assumed ones at alpha 0.45, rotates the spindle set about the display x axis at up to ±2 rev/s with a native display link, draws the wire bodies and colliding segments (red), and places the lathe insert or printer nozzle at the playhead. A machine scene suppresses the generic stock box. The review header reports kind, source, axes, turns, workholding, assumptions, mismatch, collision count and the current spin. Bodies, spin, collisions and tool identity are part of the preview `ETag`, so a changed workholding or machine setting is a new payload, not a stale 304.
- **The real toolpath visualizer and CAD canvas (2026-10-20).** Payload format 4 adds what the desktop's visualizer and CAD canvas show, all computed on the desktop:
  - **The cutter.** Every operation carries the tool it runs (diameter, cutting length, shank, stickout, nose radius and the holder), and the phone draws it as a solid at the playhead — the cutting part on the tip, the shank, the holder on top. The Metal module has its own buffer for it, because it moves with the playhead.
  - **The operations.** A program that changes tools is one toolpath per tool; the payload names every operation with the run of path segments it drew. The phone colours the path by operation with the desktop's palette, lists the operations and shows one alone.
  - **The contacts on the clock.** The setup checks and the collisions the core replays against the stock left travel as events: the desktop's own clock (`seconds`), the segment the contact happens on, the line it comes from and the sentence that says what happened. The phone lists them, seeks to the move and stops the playback there.
  - **The part.** A toolpath preview carries the drawing the program was made from, as a mesh: the phone draws the workpiece beside the path.
  - **The feature tree.** A drawing or component preview carries the features of its parametric elements, so the phone reads what a part is made of without the desktop.
  - The live stock (the material as the program removes it) and the turned profile stay desktop-only; the phone fetches no simulation.
- **Gateway policy (2026-10-17).** Commit, branch, checkout, restore, review and merge stay phone features: none loses data (restore is a new commit, checkout refuses a dirty working copy, an AI actor cannot merge into `main`). Instead of a 403 the gateway adds: per-route request-body limits (prompts 36 MiB for five base64 images, every other write 1 MiB, declared or chunked → **413**); a deadline for the desktop's response headers on non-stream routes (reads 60 s, writes 120 s → **504**), while the SSE routes (`events`, `sessions/:id/stream`, `chat/stream`) never time out; per-device budgets — 240 requests burst / 20 per s, 60 writes burst / 1 per s, 12 open streams — answering **429** with `Retry-After`; the device id travels as `x-cadcamfun-companion-device` (whatever the phone sends under that name is replaced) and the `ActivityLog` row of every history-changing action records `via: "companion:<device id>"`. One structured log line per phone request (`companion.device`, `http.method`, `http.path`, `http.status`, `http.duration_ms`, `companion.kind`, `companion.refused`) goes through the sidecar's Effect logger; never the token, a body or a query string.
- **Notifications.** `GET /api/notifications?limit=&offset=&cursor=&onlyUnread=` is newest first with the id breaking ties; `limit` 1–100 (default 20), `offset` ≤ 10 000; the reply adds `nextCursor` (opaque, null on the last page), which neither repeats nor skips rows when new notifications arrive between pages. `cursor` and `offset` are exclusive. Malformed values are a 400 with a message (they were a 500). `unreadCount` counts every unread row of the user whatever the filter or page; `PUT …/:id { isRead }` is idempotent, `mark-all-read` answers the number it changed (0 the second time).
- `GET /api/ai/status` answers `host: "nikcli" | "direct"` (required in the schema; the phone's local type may keep it optional).
- Revoking a device from the desktop cuts it off on the next request.
- Outside the home network: the gateway needs no relay when the phone can route to the desktop. The pairing screen takes any address for the desktop, so a private overlay network (Tailscale, WireGuard, a VPN) works as is: the phone still pins the certificate fingerprint and presents its device token. A hosted relay for users without such a network is not built; it would have to carry this same TLS stream end to end, never terminate it.

Phone side (`apps/mobile`):

- Pairing reliability (2026-10-17, WP13): the Swift `request` bridge accepts exactly the six JavaScript transport arguments; Expo injects `Promise` only as the final native argument. Pinned URLSession connections wait for connectivity while iOS asks for local-network access. Scan, paste, manual entry and deep links surface the actual connection error instead of replacing bridge, certificate or authentication failures with an unreachable-host message. Verify a native Release round trip on a simulator or physical device as well as the mobile tests and typecheck. Tauri capabilities govern WebView IPC, not the Bun gateway's incoming TCP listener; sandboxed macOS distribution would separately require the server network entitlement.
- `modules/companion-net/ios/CompanionNetModule.swift` — local Expo module using ephemeral URLSession connections, pinned leaf-certificate SHA-256, HTTPS-only requests and incremental UTF-8/SSE delivery. Redirects and cross-origin paths are refused; cancellation closes the task and stream subscription.
- `modules/preview` — local Expo module (`CadPreview`) that draws the workspace mesh and toolpath lines with Metal. JavaScript uploads typed arrays and the camera matrix; the module does not orbit, pick or import the CAD kernel. It copies those arrays into private buffers, skips a draw that would read past them, and reports one stable sentence when Metal cannot start. Shader and command-buffer detail stays in the unified log (`com.cadcamfun.companion`).
- `lib/native.ts` — optional native-module loading keeps Expo Go imports from crashing routes. Native connection requires `CompanionNet`; unsupported platforms and web never silently replace pinning with ordinary fetch. SecureStore holds pairing credentials. Test clients inject an explicitly verified transport.
- Expo Router routes own pairing, project resources, assistant sessions, notifications and preferences. Reconnect retains credentials for an offline desktop, checks health without overlapping probes, and cancels stale resource/chat requests when the client/project/screen changes. `cadcamfun://pair` opens the dedicated pairing route without exposing the token in UI/logs.

`.github/workflows/ios.yml` generates the Expo iOS project, builds an unsigned Release simulator app with CocoaPods/Xcode, installs it, opens a real pairing deep link and checks gateway authentication and project reads. Before boot it writes the LaunchServices scheme approval (`com.apple.CoreSimulator.CoreSimulatorBridge-->cadcamfun`) so `simctl openurl` delivers `cadcamfun://pair` instead of stopping on the iOS "Open in CADCAMFUN?" prompt, then resends the link if the router was not mounted yet. The same workflow also runs on pull requests that touch `apps/mobile` or the workflow file. The CI mobile job typechecks, tests and exports the iOS JavaScript bundle. These replace commands for the removed Tauri/Rust mobile shell. Local native compilation and simulator startup must pass before recording that validation; the workflow definition alone is not proof of a successful CI run. Device/TestFlight signing still requires the owner's Apple team and certificates.

**The assistant from the phone, end to end.** `companion-chat-e2e.test.ts` boots the real sidecar process (embedded nikcli host), points MiniMax at a scripted OpenAI-compatible server through `CADCAMFUN_AI_MINIMAX_BASE_URL` (also usable for a regional endpoint or a corporate proxy), pairs a phone client over pinned TLS and sends a chat message through the gateway. The scripted model calls `vcs_start_change`, `cad_add_entities`, `vcs_commit`, `vcs_open_pull_request`; the test then reads, as the phone, an open AI pull request on an `ai/*` branch with the drawing change in it, checks that `main` still holds only the human commit, and that merging is a separate action by a person. It uses the same `CompanionClient` code as the app. It proves the plumbing and the guard rails, not the quality of a real model's decisions.

## 7. GitHub mirror

`restTransport` + `push`/`pull` are implemented and tested against an in-memory remote that enforces fast-forward-only updates and verifies every object hash. The HTTP routes (`GET/PUT /vcs/remote`, `POST /vcs/push|pull`) exist: the desktop screen keeps the GitHub token in the OS keychain and sends it per request; the sidecar never stores it, and the companion gateway refuses these routes. Not done: mirroring PRs to GitHub PRs (`PullRequest.remoteNumber` is reserved), and a live check that GitHub's Git Data API reproduces the exact commit oid for a given author/committer date (unit tests prove the hash logic, not GitHub's behaviour).

## 8. Limits and next steps

1. Run the iOS shell on a device (Mac), APNs push for PR/Actions events, remote access beyond the LAN.
2. Desktop UI: `Version control` screen (`/projects/:id/history`: changes + commit, history with property-level diffs and restore, branches, pull requests with review/merge, Actions runs, GitHub push/pull) and per-item History buttons are built; a drawn commit-graph view and in-editor (CAD/CAM) history panels are not.
3. `needs`-scoped outputs if workflows grow (today step outputs are shared run-wide, keyed by step id).
4. GitHub routes and PR mirroring (§7); `deletedAt`/sync interplay with `10-release-sync.md` §5 (git history supersedes the change-log idea there).
5. Large binary assets (STL/DXF imports): store as blobs; packfile/delta compression is not implemented (object count per project stays small; revisit with real data).
6. `log` is O(history) per call and `isAncestor` walks the graph; fine for thousands of commits, add commit-graph caching if projects grow beyond that.
7. **Two companion features still need infrastructure the phone cannot provide alone.** *APNs*: the phone can ask for the permission and hold a token, but the desktop must own the APNs key, the registration route and the send, and the owner's Apple team has to sign it — until then the phone's "something happened" signal is the unread badge on the Activity tab and the feed that refreshes itself. *Account sign-in*: the sidecar's identity flow is a desktop loopback callback, and the phone needs its own PKCE flow against the issuer (`cadcamfun://auth/callback`) plus an identity header through `modules/companion-net`; both need the issuer to be live and a native rebuild of the installed app.
