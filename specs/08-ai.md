# WP8 — AI layer (`packages/ai`)

Status: todo. Owner dir: `packages/ai`. No dependency on `db`, `api`, or the sidecar; the sidecar adapts this package (WP4 `AiService`).

**Base and provider: nikcli** via the embedded host `@nikcli-ai/sdk-next` (source: `github.com/nikcli/nikcli`, `packages/sdk-next`, `packages/llm`, `packages/sdk/openapi.json`). **AI SDK v7** (`ai@7.0.127` + `@ai-sdk/*`) is used for direct, single-shot model calls and as the fallback path. Everything is exposed to the rest of the app as Effect services (`effect@4.0.0-rc.112`, the version `sdk-next` pins; the whole workspace is on this exact version so Layers and `Context` tags are shared).

Read first: `packages/db/node_modules/effect/ai-docs/src/` (Effect rc.112 docs; Bun does not hoist, so use any workspace package's `node_modules/effect/ai-docs`), `packages/ai/node_modules/ai/docs/` (AI SDK v7), and the nikcli sources above (`sdk-next/src/{index,nikcli,tool}.ts`, `sdk-next/test/embedded.test.ts` is the best usage example).

Legacy reference (behaviour only): `.reference/src/lib/ai/provider/*` (a project-local copy inspired by nikcli's `@nikcli-ai/llm`), `.reference/src/lib/ai/{prompt-templates,cadActionHandler,camActionHandler,unifiedAIService}.ts`, `.reference/src/lib/ai/mcp/`.

## 1. Architecture

```
UI ──► sidecar `ai` HttpApi group ──► AiService (this package)
                                        ├─ NikCliAgent   (primary)  @nikcli-ai/sdk-next embedded host: sessions, tool loop, provider/model routing
                                        └─ DirectModel   (fallback + one-shot calls)  `ai` v7 generateText/streamText + @ai-sdk/{anthropic,openai,openai-compatible,gateway}
```

- **Primary path (NikCli)**: `NikCli.create({ directory })` gives the generated HTTP-API client running in-process (no listener, no network) plus `tools.register(...)`. Conversations are nikcli **sessions** (`session.create`, `session.prompt`, `session.messages`, `session.abort`); nikcli owns the agent loop, provider selection (`provider.list`, `config.providers`), and streaming events.
- **CAD/CAM tools** are registered into the host with `nikcli.tools.register(Tool.define(id, async () => ({ description, parameters: zod, execute })))`. Handlers are supplied by the caller (the sidecar) so this package has no storage dependency. Parameter schemas are **zod 4** (required by nikcli); every handler re-validates its input with the matching Effect Schema from `@cadcamfun/core` before touching data, and a test asserts zod and Effect schemas accept/reject the same fixtures.
- **Fallback / one-shot path (AI SDK v7)**: `DirectModel` wraps `generateText`/`streamText`/`isStepCount` from `ai` with models built by `createAnthropic`, `createOpenAI`, `createOpenAICompatible` (MiniMax and any OpenAI-compatible base URL) and `createGateway`. It is used when nikcli is unavailable or for stateless calls that don't need a session (G-code analysis summaries, structured output with `Output`, title generation). Effect wrapping: `Effect.tryPromise` for `generateText`, `Stream.fromAsyncIterable` for `streamText().fullStream`, with `AbortSignal` wired to fibre interruption.

### Hard safety requirements for the embedded host

nikcli ships coding-agent tools (`bash`, file edit/write, web, etc.) and reads the *user's* nikcli configuration and credentials. A CAD application must not expose any of that to a model.

1. **Isolated state**: before `NikCli.create`, set `XDG_DATA_HOME`, `XDG_CACHE_HOME`, `XDG_CONFIG_HOME`, `XDG_STATE_HOME` and `NIKCLI_TEST_HOME` to folders under the app data dir (`<dataDir>/ai/nikcli/…`) and `NIKCLI_DISABLE_PROJECT_CONFIG=1` (the same variables `sdk-next`'s own tests use). The host must never read `~/.config/nikcli` or `~/.nikcli`. Test: with a sentinel file placed in a fake `$HOME/.config/nikcli`, the host never reads it.
2. **Locked-down agent**: define a dedicated agent `cadcam` (via `config.update`/agent config) whose allow-list is **only** the tools registered by this package. Test: `experimental.toolIDs()` for the agent contains none of `bash`, `edit`, `write`, `webfetch`, shell/file tools; a scripted prompt asking to run a shell command results in no tool execution.
3. **Permissions**: permission mode `default`; the `cadcam` agent never auto-approves. Any permission request is surfaced to the UI as a typed event (destructive CAD tools already require `confirm: true`, see §3).
4. **No credentials in logs/state**: keys pass only through `Redacted`; log capture test with a sentinel key.
5. `directory` is a fixed per-project scratch folder inside the app data dir, never the user's project/home directory.

## 2. Providers and credentials

| Provider id | Path | Credential |
| --- | --- | --- |
| `anthropic` | nikcli provider; direct: `@ai-sdk/anthropic` | API key |
| `openai` | nikcli provider; direct: `@ai-sdk/openai` | API key |
| `minimax` | nikcli openai-compatible provider; direct: `@ai-sdk/openai-compatible`, default base `https://api.minimax.io/v1` (override e.g. `https://api.minimaxi.com/v1`) | API key (pay-as-you-go or token-plan key) |
| `gateway` | `@ai-sdk/gateway` / nikcli | gateway key |

Resolution (same rule as the legacy app): direct vendor when its key is configured, otherwise `gateway`; `forceGateway` routes everything through it.

### Provider catalogue

`ProviderId` is a **string**, not a closed union: nikcli merges the whole models.dev database with `nikcli.json`, so `provider.list()` is the single source of truth for "which providers and models can this app talk to" (`src/nikcli/catalog.ts`). The four rows above are the ones we *configure* (base URL / protocol, `defaultProviderSpecs`); every other provider is served by the host and only needs a key.

- With `NIKCLI_DISABLE_MODELS_FETCH=1` the host neither downloads models.dev nor falls back to its embedded snapshot, so `provider.list()` answers with the four declared providers. `makeNikCliRuntime` therefore seeds `<cache>/models.json` once (`src/nikcli/models-cache.ts`): a single request to `https://models.dev/api.json`, only while the file is missing, only when `catalogue.network` is on (the sidecar enables it unless `CADCAMFUN_AI_OFFLINE=1`, which tests set). The seed never blocks boot — it is a promise the catalogue reads await (`runtime.catalogueReady`).
- `PUT`/`DELETE /ai/credentials` validate the provider id syntactically **and** against `GET /ai/providers`, so a typo can never become a key that nobody reads (400 `Unknown provider`).
- `AiCredentials.status` reports the built-in providers **plus** every provider that has a stored key, so a models.dev provider stays visible (and removable) once configured.
- The one-shot AI SDK path (`DirectModel`) still only builds clients for the four built-ins (`BUILTIN_PROVIDER_IDS`); any other provider throws a config error asking for a base URL.

Credentials never live in env or SQLite. The Tauri shell holds them in the OS keychain (`07-tauri-shell.md`). At boot the UI reads them via `secret_get` and calls the sidecar's `PUT /ai/credentials`; `AiCredentials` (`Context.Service`) then pushes them into the embedded nikcli host with its provider API (`POST /provider/{providerID}/api` = `provider.api.set`) and into `DirectModel`'s in-memory map. Nothing is persisted outside the isolated nikcli state folder from §1 (verify what nikcli writes there and document it; if it persists keys in plaintext, clear them on `AiCredentials.clear` and on shutdown, or keep keys memory-only).

```ts
class AiCredentials extends Context.Service<AiCredentials, {
  set(provider: ProviderId, key: Redacted.Redacted<string>, opts?: { baseUrl?: string }): Effect<void, AiConfigError>
  clear(provider: ProviderId): Effect<void>
  status: Effect<Record<ProviderId, "configured" | "missing">>
}>()("cadcamfun/AiCredentials") {}
```

## 3. Public surface

```ts
class AiService extends Context.Service<AiService, {
  models: Effect<ReadonlyArray<ModelInfo>, AiConfigError>                       // id, provider, context window, tools/vision flags
  providers: Effect<ReadonlyArray<ProviderEntry>, AiConfigError>                // catalogue: id, name, source, auth, configured, models[]
  chat(input: { sessionId?: string; message: string; context: ChatContext; model?: ModelSelector }): Stream<AiEvent, AiError>
  analyzeGcode(input: { gcode: string; machine?: MachineProfile }): Effect<GcodeReport, AiError>   // deterministic checks + optional LLM summary
  generate<A>(input: { prompt: string; schema: Schema.Schema<A>; model?: ModelSelector }): Effect<A, AiError>  // DirectModel + Output
  abort(sessionId: string): Effect<void>
}>()("cadcamfun/AiService") { static layer: Layer<AiService, AiConfigError, AiCredentials | ToolHandlers> }

AiEvent = delta | tool_call | tool_result | permission_request | done | error     // shared with the SSE contract in WP3
ModelSelector = { provider?: ProviderId; model?: string; tier?: "fast" | "balanced" | "best" }
```

- `GET /ai/providers` answers with `providers` (per-provider models with context window, output cap, cost, tools/vision flags and auth methods) for the settings browser; `GET /ai/models` stays the flat, key-filtered list the model picker uses. Both are cached for a minute (`catalogOf`) — the catalogue is the whole models.dev database. When there is no host, `providers` answers with the built-ins and their tier defaults, so no provider ever shows zero models.
- `ProviderId = string` in the wire contract (`AiProviderId`): the API accepts any provider id the host knows.

- A single `models.ts` maps `tier → model id` per provider; no model ids anywhere else.
- Errors are tagged (`AiConfigError`, `AiProviderError`, `AiAborted`) and mapped to the API-level `AiFailure` Schema in WP3.
- `ToolHandlers` is a `Context.Service` the sidecar provides: `addEntities`, `addElements`, `modifyEntities`, `deleteEntities`, `describeDrawing`, `createOperation`, `listOperations`, `updateOperation`, `suggestParameters`, `generateGcode`, `verifyOperation`, `lookupMaterial`, `lookupTool`.

### Tool catalogue

| Tool id | Purpose | Notes |
| --- | --- | --- |
| `cad_add_entities` | Append 2D entities to the active drawing | validated with WP1 `Entity` Schema |
| `cad_add_elements` | Build 3D and 2D geometry in the editor's own element format: solids, extrusion, revolution, sweep, loft, booleans, curves, mechanical parts, architecture | `packages/ai/src/element-catalog.ts` is the single table (defaults, required fields, minimum counts); invalid input adds nothing and lists every problem; a number in `operands` is the index of an earlier element of the batch |
| `cad_modify_entities` / `cad_delete_entities` | Edit by id | delete requires `confirm: true` |
| `cad_describe_drawing` | Counts, bounds, layers | read-only |
| `cam_create_operation` | Add a CAM operation | WP2 params Schema |
| `cam_generate_gcode` | Run the pipeline, return stats + first N lines | read-only |
| `cam_list_operations` / `cam_update_operation` | List the drawing's operations; change their settings (drops the stale G-code) | settings re-decoded with the WP2 generator Schema |
| `cam_suggest_parameters` | Suggested depth/stepdown, cutting statistics, warnings | pure `generator.suggestFor` |
| `cam_verify_toolpath` | Simulate an operation's G-code on its stock: removal, rapids in material, shank/holder/fixture collisions, cutting below the stock, gouges against `targetSolids` | pure `cam.verify` (spec 04 §10); holder, fixtures and target are modelled only when given, and the reply says which were |
| `cam_analyze_gcode` | Static checks (travel limits, rapids through material, missing spindle start, feed anomalies) | deterministic code in `core`/this package, not an LLM |
| `lib_lookup_material` / `lib_lookup_tool` | Read the library | read-only |

Tool results are small, structured, and never include secrets or filesystem paths.

## 4. Prompts and flows

- System prompts live in `prompts/*.md` (text imports) with a `{{variable}}` renderer covered by tests. English only.
- Flows: `chat` (nikcli session, tool-using), `designFromText` (text → entities), `optimizeToolpath` (explain/suggest only, never silently applies), `reviewGcode` (runs `cam_analyze_gcode`, summarises).
- History: nikcli sessions hold conversation state inside the isolated nikcli folder; the `Conversation`/`Message` DB tables are deferred, so the UI stores nothing about chats beyond the session id.

## 5. Testing (no network, no real keys)

- **NikCli host tests**: modelled on `sdk-next/test/embedded.test.ts` (temp dirs, isolated env vars, `Instance.disposeAll()` in `afterEach`). Cover: tool registration/visibility, locked-down agent (§1.2), isolated state (§1.1), credentials push, session create/list/abort.
- **Model stubbing**: a fake provider (nikcli custom/openai-compatible provider pointing at a local `Bun.serve` that replays scripted SSE completions) drives end-to-end `chat` tests including a scripted tool call → handler → result → final text. For `DirectModel`, use `MockLanguageModelV4` from `ai/test` (v7).
- Provider-resolution matrix (key present/absent/gateway forced), Effect↔zod schema agreement, prompt renderer, `analyze_gcode` on fixtures covering each legacy bug class in `04-core-cam.md` §5, no key in logs.
- **Offline by default**: tests set `CADCAMFUN_AI_OFFLINE=1` (`apps/sidecar/test/helpers.ts` sets it for the whole process), which turns the models.dev seed into a `skipped` answer — a reachable fetch would otherwise stall the sidecar boot by 10 s.
- **One process, one host**: `bun test` runs every file in a single process, so `loadSdk` imports `@nikcli-ai/sdk-next` with `Error.prepareStackTrace` reset around it. Once any UI file leaves Bun's source-map rewriter installed, `Error.captureStackTrace` rejects the plain objects axios brands as errors while following redirects, and the host used to fail to load with `First argument must be an Error object` the moment any desktop test ran first (`apps/desktop/test/host-load.test.ts`). Host tests share one data dir (`sharedDataDir` in `packages/ai/test/helpers/host-env.ts`).
- A manual `bun run --filter @cadcamfun/ai smoke` script exercises real providers when keys are in the shell env; excluded from `bun test`.

## 6. Packaging risks (resolve early, record results here)

1. **Typings**: `@nikcli-ai/sdk-next@1.428.0` ships `index.js` only (no `.d.ts`). Add an ambient declaration file in this package covering the surface actually used (`NikCli.create/layer/Service`, `Tool.define`, `ClientError`, and the client methods in §1), or generate types from the upstream sources; keep it small and tested via `tsc`.
2. **Weight/native deps**: the package is ~20 MB with 60 dependencies (TUI, chat adapters, `@parcel/watcher`, `@ff-labs/fff-bun`, …). Verify `bun build --compile` of the sidecar still produces a working binary on macOS/Windows/Linux. If it doesn't, run the NikCli host in a lazily started **separate Bun process** (`apps/sidecar` spawns it, talks over a Unix socket/loopback with its own token) and keep the same `AiService` interface; document the outcome and update `05-api-sidecar.md` §3 and `10-release-sync.md`.
3. **Version coupling**: `sdk-next` hard-pins `effect@4.0.0-rc.112`; the workspace must stay on that exact version until `sdk-next` moves. Upgrading `effect` is a single coordinated change across all packages.
4. `sdk-next` is documented upstream as *transitional* (it will replace `@nikcli-ai/sdk`); pin the exact version `1.428.0` and isolate all imports behind `src/nikcli/` so a future API change touches one folder.

## 7. Acceptance criteria

- `chat` completes a scripted tool-calling conversation end to end through the embedded nikcli host and yields the typed `AiEvent` stream.
- With the real `~/.config/nikcli` present on the machine, tests prove it is not read, and the `cadcam` agent exposes zero built-in shell/file tools.
- `DirectModel` one-shot structured output works against `MockLanguageModelV4`.
- No API key appears in logs, errors, or serialised state.
- `bunx tsc -p packages/ai/tsconfig.json` clean; only workspace dependency is `@cadcamfun/core`.

### Skills (tailored playbooks for the base agent)

nikcli is the base; what makes it a CAD/CAM assistant is what we install into its isolated config: our tools (`toolsFor`), the locked-down `cadcam` agent, and **skills**. `packages/ai/src/skills/index.ts` holds six playbooks (`cad-3d-modeling`, `cam-operation-workflow`, `toolpath-verification`, `cutting-parameters`, `drilling-and-holes`, `stock-and-fixtures`). `installSkills` writes them as `<config>/skills/<name>/SKILL.md` every time the host config is written (our folders are replaced, other folders are left alone), nikcli lists them to the model, and the agent loads one with its `skill` tool, which is the only built-in tool the permission rules allow besides ours. Tests: every skill is well formed, every tool a skill names exists in `TOOL_IDS`, `installSkills` is idempotent, and the real embedded host discovers all of them (`client["top-level"].skill()`). To change what the assistant knows, edit that file; to give it a new ability, add a tool to `tools/catalogue.ts` and say when to use it in a skill.

### Workspace integration (CAD, CAM and the assistant as one document)

- **One document.** `cad/store/documentStore.ts` holds the stored project and drawing the editor belongs to (set when a drawing is opened, saved as a project, or adopted from a tool result). Before every message `prepareWorkspace` (`ai/drawing-context.ts`) makes sure it exists (the newest project, or a new "Untitled project", and its newest drawing) and writes the live elements into it, which also makes it the newest drawing the sidecar tools pick. A missing project or drawing is never a reason to refuse a message.
- **Context from what is on screen.** `currentDrawingContext` is built from the elements, selection and layer stores, the workpiece, the generator settings, the CAM program and G-code, and the last verification (`not-run | stale | ok | errors` with the first findings); `page` says whether the user is in CAD or CAM. It replaces the old context built from `app.drawing()`.
- **Tool results show on screen.** `ai/editor-sync.ts` applies `cad_add_*`, `cad_modify_entities` and `cad_delete_entities` to the elements store with the same ids (layers found by name or created); `ai/cam-sync.ts` reads the operation back after `cam_create_operation`, `cam_update_operation`, `cam_generate_gcode` and `cam_verify_toolpath` and fills the generator settings, the editor and preview, and the Verify tab. `verifyOperation` stores the full report on the operation (`data.verification`) together with the G-code it is about.
- **Asking the assistant.** `ai/ask.ts`: the browser toolbar (selection) and the Verify tab (errors) open the docked panel and send a prompt that names the ids / findings; suggestions turn into "Verify the toolpath" and "Fix the verification errors" from the verification state.
- Limits: the live editor is copied into the stored drawing when a message is sent, not continuously; edits made in the editor while the assistant is answering are overwritten by its next tool result for the same element ids only.
