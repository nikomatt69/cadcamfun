## 1. Architecture

Project-workspace refinement requested on 2026-10-13 is governed by `24-assistant-control-flow.md`: retain one application runtime with cached native directory Instances, restore native session identity across restarts, isolate project context/conversations and deepen the existing chat UI. This does not change the ordered roadmap or claim a new geometry/manufacturing engine.

```
UI ──► sidecar `ai` HttpApi group ──► AiService (this package)
                                        ├─ NikCliAgent   (primary)  @nikcli-ai/sdk-next embedded host: sessions, tool loop, provider/model routing
                                        └─ DirectModel   (fallback + one-shot calls)  `ai` v7 generateText/streamText + @ai-sdk/{anthropic,openai,openai-compatible,gateway}
```

- **Primary path (NikCli)**: `NikCli.create({ directory })` gives the generated HTTP-API client running in-process (no listener, no network) plus `tools.register(...)`. Conversations are nikcli **sessions** (`session.create`, `session.prompt`, `session.messages`, `session.abort`); nikcli owns the agent loop, provider selection (`provider.list`, `config.providers`), and streaming events.
- **CAD/CAM tools** are registered into the host with `nikcli.tools.register(Tool.define(id, async () => ({ description, parameters: zod, execute })))`. Handlers are supplied by the caller (the sidecar) so this package has no storage dependency. Parameter schemas are **zod 4** (required by nikcli); every handler re-validates its input with the matching Effect Schema from `@cadcamfun/core` before touching data, and a test asserts zod and Effect schemas accept/reject the same fixtures.
- **Fallback / one-shot path (AI SDK v7)**: `DirectModel` wraps `generateText`/`streamText`/`isStepCount` from `ai` with models built by `createAnthropic`, `createOpenAI`, `createOpenAICompatible` (MiniMax and any OpenAI-compatible base URL) and `createGateway`. It is used when nikcli is unavailable or for stateless calls that don't need a session (G-code analysis summaries, structured output with `Output`, title generation). Effect wrapping: `Effect.tryPromise` for `generateText`, `Stream.fromAsyncIterable` for `streamText().fullStream`, with `AbortSignal` wired to fibre interruption.

### Hard safety requirements for the embedded host

nikcli ships coding-agent tools (`bash`, file edit/write, web, etc.) and reads the *user's* nikcli configuration and credentials. A CAD application must not expose any of that to a model.

1. **Isolated state**: before `NikCli.create`, set `XDG_DATA_HOME`, `XDG_CACHE_HOME`, `XDG_CONFIG_HOME`, `XDG_STATE_HOME` and `NIKCLI_TEST_HOME` to folders under the app data dir (`<dataDir>/ai/nikcli/…`) and `NIKCLI_DISABLE_PROJECT_CONFIG=1` (the same variables `sdk-next`'s own tests use). The host must never read `~/.config/nikcli` or `~/.nikcli`. Test: with a sentinel file placed in a fake `$HOME/.config/nikcli`, the host never reads it.
2. **Locked-down agent**: define a dedicated agent `cadcam` (via `config.update`/agent config) whose allow-list is **only** the tools registered by this package. Test: `experimental.toolIDs()` for the agent contains none of `bash`, `edit`, `write`, `webfetch`, shell/file tools; a scripted prompt asking to run a shell command results in no tool execution.
3. **Permissions**: permission mode `default`; the `cadcam` agent never auto-approves. Any permission request is surfaced to the UI as a typed event (destructive CAD tools already require `confirm: true`, see §3).
4. **No credentials in logs/state**: keys pass only through `Redacted`; log capture test with a sentinel key.
5. `directory` is a fixed per-project scratch folder inside the app data dir, never the user's project/home directory.

### Provider catalogue

`ProviderId` is a **string**, not a closed union: nikcli merges the whole models.dev database with `nikcli.json`, so `provider.list()` is the single source of truth for "which providers and models can this app talk to" (`src/nikcli/catalog.ts`). The four rows above are the ones we *configure* (base URL / protocol, `defaultProviderSpecs`); every other provider is served by the host and only needs a key.

- With `NIKCLI_DISABLE_MODELS_FETCH=1` the host neither downloads models.dev nor falls back to its embedded snapshot, so `provider.list()` answers with the four declared providers. `makeNikCliRuntime` therefore seeds `<cache>/models.json` once (`src/nikcli/models-cache.ts`): a single request to `https://models.dev/api.json`, only while the file is missing, only when `catalogue.network` is on (the sidecar enables it unless `CADCAMFUN_AI_OFFLINE=1`, which tests set). The seed never blocks boot — it is a promise the catalogue reads await (`runtime.catalogueReady`).
- `PUT`/`DELETE /ai/credentials` validate the provider id syntactically **and** against `GET /ai/providers`, so a typo can never become a key that nobody reads (400 `Unknown provider`).
- `AiCredentials.status` reports the built-in providers **plus** every provider that has a stored key, so a models.dev provider stays visible (and removable) once configured.
- The one-shot AI SDK path (`DirectModel`) still only builds clients for the four built-ins (`BUILTIN_PROVIDER_IDS`); any other provider throws a config error asking for a base URL.

**Update (owner decision):** the keys are also kept in `<data dir>/ai/credentials.json` (`jsonFileCredentials`, written atomically with mode 0600, loaded when the sidecar starts, rewritten on every set/clear, a missing or damaged file reads as empty), so they are not asked for again after a restart; clearing a key removes it from the file. Shutdown clears the host's copy only, never the file. Credentials never live in env or SQLite. The Tauri shell holds them in the OS keychain (`07-tauri-shell.md`). At boot the UI reads them via `secret_get` and calls the sidecar's `PUT /ai/credentials`; `AiCredentials` (`Context.Service`) then pushes them into the embedded nikcli host with its provider API (`POST /provider/{providerID}/api` = `provider.api.set`) and into `DirectModel`'s in-memory map. Nothing is persisted outside the isolated nikcli state folder from §1 (verify what nikcli writes there and document it; if it persists keys in plaintext, clear them on `AiCredentials.clear` and on shutdown, or keep keys memory-only).

## 3. Public surface

```ts
class AiService extends Context.Service<AiService, {
  models: Effect<ReadonlyArray<ModelInfo>, AiConfigError>                       // id, provider, context window, tools/vision flags

AiEvent = delta | tool_call | tool_result | permission_request | done | error     // shared with the SSE contract in WP3

```

- `GET /ai/providers` answers with `providers` (per-provider models with context window, output cap, cost, tools/vision flags and auth methods) for the settings browser; `GET /ai/models` stays the flat, key-filtered list the model picker uses. Both are cached for a minute (`catalogOf`) — the catalogue is the whole models.dev database. When there is no host, `providers` answers with the built-ins and their tier defaults, so no provider ever shows zero models.
- `ProviderId = string` in the wire contract (`AiProviderId`): the API accepts any provider id the host knows.

- **CAD/CAM programmer agent**: the stateful project-scoped chat runs the nikcli host agent with CAD and CAM tools, bounded specialist agents, and visible tool events. It builds and edits geometry and components, transforms/groups parts, manages layers, supports parametric designs, looks up materials and tools, configures machining, generates G-code, analyses it and simulates toolpaths. Mutations go through validated tools; stateless HTTP workflows return suggestions only.
- **Endpoint map**: `GET /api/ai/prompts?mode=...`; `POST /api/ai/title`; `POST /api/ai/design-analysis`; `POST /api/ai/machining-parameters`; `POST /api/ai/gcode-optimization`; `POST /api/ai/design-suggestions`. Contracts live in WP3's AI group and handlers in WP4. Each model-backed endpoint accepts the shared provider/model/tier selector. G-code optimization never writes to a project.
- **Context and cache**: workspace snapshots and assistant notes use sidecar `KvStore` backed by `LocalKeyValue` (SQLite/Drizzle/Effect); credentials are excluded. Successful stateless model workflows use a bounded in-memory LRU keyed by normalized input, model selector and credential revision. Failures are not cached. The provider catalogue keeps its separate 60-second cache. Session chat and mutations are never cached.

- A single `models.ts` maps `tier → model id` per provider; no model ids anywhere else.
- Errors are tagged (`AiConfigError`, `AiProviderError`, `AiAborted`) and mapped to the API-level `AiFailure` Schema in WP3.
- `ToolHandlers` is a `Context.Service` the sidecar provides: `addEntities`, `addElements`, `modifyEntities`, `deleteEntities`, `describeDrawing`, `createOperation`, `listOperations`, `updateOperation`, `suggestParameters`, `generateGcode`, `verifyOperation`, `lookupMaterial`, `lookupTool`.

### Workspace integration (CAD, CAM and the assistant as one document)

A missing project or drawing is never a reason to refuse a message.
- **Context from what is on screen.** `currentDrawingContext` is built from the elements, selection and layer stores, the workpiece, the generator settings, the CAM program and G-code, and the last verification (`not-run | stale | ok | errors` with the first findings); `page` says whether the user is in CAD or CAM. ### Tool prompts, machines and design (nikcli's architecture on CADCAMFUN)

- **Context** (`packages/ai/src/workspace-context.ts`): the desktop keeps a JSON snapshot of the workspace in `ai.context.<projectId>`; the sidecar renders it as short sections inside a character budget (default 6,000): document and units (tool calls in mm, what the user reads, the tolerance in mm and µm), the selection, model counts, layers, stock, machine/controller/post/material/operation/tool/offset, toolpaths, verification state with its first findings, G-code size, attached files, then the element list (full ids: the tools need them) and a G-code preview, which shrink first and say how many were left out. Saved notes are capped (1,500 characters, newest first). The system prompt says the snapshot is from send time and tool results win.
- **Sessions** (nikcli-style): the assistant panel lists conversations (newest first), reopens one with its text (kept on the device by `persisted.ts`: 20 conversations x 60 messages, tool traffic not kept), renames it in place, deletes it with a confirmation (local text and, through `POST /api/ai/sessions/remove`, the host's session) and starts a new one. A reopened conversation continues in the host's session while it still exists; otherwise the host starts a fresh one and the earlier text is only history on screen.
- **The agent loop is the host's** (nikcli: `session/prompt.ts`, `processor.ts`, `retry.ts`, `goal.ts`; primary agents have a 25-step configuration hint plus an enforced stream guard; ordinary chat carries a stopped turn on up to eight times while its plan has open items, its last call failed or it explicitly announced an action. Explicit goals retain 50 continuations and a 250-step guard per native command; repeated failures or exhausted continuation budgets end with an error, preserving completed changes): the model calls tools, reads their results and calls again until it stops, with no "continue" from the user. What the host does is shown, not hidden: the stream carries `step` (start/finish with tokens), `reasoning`, `tool_progress` (a tool call still being written, with its size, so a long call is visibly alive), `todo` (the agent's plan from the host's `todowrite`, whole list every time), `goal` (the host's `/goal` loop: the agent calls `create_goal` for a multi-part request, the host keeps prompting until `update_goal complete|blocked`, within an iteration and token budget), `retry` (provider failure being retried) and `compacted` (the conversation was summarised). The agent's permissions add `todowrite`, `todoread`, `create_goal`, `get_goal`, `update_goal` (data only) beside our tools and `skill`; the desktop does not reject them as unknown tools (`HOST_TOOLS`). The panel shows goal, plan checklist, step, tool being written, retry and reasoning (`AgentActivity`).
- **Native retries and turn recovery.** The pinned nikcli processor owns provider retry admission/backoff; the adapter does not abort a call after an arbitrary number of native retry events. Only settled transient failures may resume a turn (up to 3 times, 5 s doubling), preserving completed work and inspecting uncertain mutations. Auth, quota, context-length, terminal refusals and user questions do not receive automatic continuation nudges. `cad_add_elements` retains valid elements and reports invalid indices under `skipped`; recovery corrects only that subset. Completed-step usage is accumulated once, including tool-loop steps.
- **A turn never depends on the connection** (nikcli's model: the turn belongs to the host session). The answer stream carries a `heartbeat` event every 5 s (`withHeartbeat`), and the sidecar server has no idle timeout (Bun closes a silent connection after 10 s, which is shorter than a model needs to write a long tool call; the client used to report that as "Decode error (200 POST ...)"). If the connection still drops, the host keeps working (the stream's teardown no longer aborts the session; only `POST /api/ai/chat/abort` does) and the client recovers: it asks `POST /api/ai/sessions/state` until the turn is idle, then shows the finished answer (`done` with `recovered: true`), and the editor catches up with the stored drawing. A stream that stops without its closing event is treated as cut, not finished. `cad_add_elements` takes at most 40 elements per call (`MAX_ELEMENTS_PER_CALL`): a call is written token by token and a long one is cut off by the model's output limit.
- **Attachments** (`packages/ai/src/attachments.ts`): a chat message may carry up to 5 files (`attachments: [{name, mime?, data, encoding}]` on `POST /api/ai/chat/stream`). Images (png, jpeg, webp, gif; 5 MB) go to the model as file parts, so it can read a drawing or a photo; text files (DXF, SVG, G-code, CSV, TXT, JSON, ...; 2 MB) are kept per project for the tools (`cad_import_drawing {attachment: "plate.dxf", depth}`) and, when short, shown in the message. What cannot be read (type, size, count) is listed in the message as "NOT read", never dropped silently. The UI has a paperclip button, removable chips and the names under the sent message.
- **User skills** (`packages/ai/src/skills/user.ts`): the user loads a `SKILL.md` (front matter `name`, `description`, then the playbook; name `a-b-c`, description one line <= 300 chars, body <= 20,000 chars, at most 50) in Settings -> AI. They live in `<dataDir>/ai/skills/<name>/`, are validated before touching the disk (built-in names are reserved), are written next to the built-in skills in the host config with a `.user-skill` marker (deleted skills disappear on the next write) and the live host reloads (`runtime.reloadSkills()`). A skill is text: it cannot run anything or widen the agent's permissions. API: `GET /api/ai/skills`, `PUT /api/ai/skills` (`{markdown}` or `{name, description, body}`), `DELETE /api/ai/skills/:name`.
- **One definition per tool** (`packages/ai/src/tools/<tool_id>.ts`, nikcli style): `defineTool("<id>", { parameters, execute })` with the description read from the tool's `.txt`; `execute(input, { handlers, projectId })` is the tool's action on the sidecar's handlers and returns a JSON-safe value. `registry.ts` lists the built-in tools (`BUILT_IN_TOOLS`, `TOOL_IDS`, `buildTools(handlers, projectId, extensions?)`); extension tools (any `ToolDefinition`, e.g. from a plugin) are passed as `extensions` and registered beside them (a repeated id is refused). `handlers.ts` holds `ToolHandlersShape`; `catalogue.ts` re-exports all of it. `cad_import_drawing` (DXF/SVG text or attachment + `depth`; STEP attachment, which brings its own height and takes `up`) builds 3D from a drawing with `cad.extrudeDrawing` (STEP: `cad.readStepShapes`, a prismatic reader: the lowest down-facing planar face gives the outline and holes, Z extent the height; steps, floors, slopes and free-form faces are counted in warnings, not read): outlines chained within `gap`, circles and inner loops as holes (boolean-subtract), open outlines reported, never guessed.
- **One `.txt` prompt per tool** (`packages/ai/src/tools/prompts/<tool_id>.txt`, loaded as text like nikcli's own tool prompts): what the tool is for, when to use it and when not, every parameter with its unit, the shape of the result, errors and what to call next. The model reads the file as the tool's description. `tool-prompts.test.ts` guarantees one file per tool, that every parameter is documented, that nothing it promises is false (operation types, tool types and materials decode in the generator; every verification code is named), and that the prompts stay within a size limit.
- **Machines**: `cam_describe_machine` returns the kinematics table (what turns, the sense of every axis, zeros, operations, settings, origins) for a mill, lathe or printer; `cam_analyze_gcode` takes `machineType` and adds the axis checks; `cam_create_operation` takes `machineType`, the zero settings and the probing settings, and a lathe or probing operation needs no drawing elements.
- **Design**: `cad_check_design` returns the model's findings and the design space (axes, planes, angle units, solid axes). `rotation` is in DEGREES (the editor's unit), arc and revolution angles in radians.
- **Skills** are now ten: cad-3d-modeling, cam-operation-workflow, toolpath-verification, cutting-parameters, drilling-and-holes, precision-and-tolerances, machines-and-axes, drawings-and-images (DXF/SVG/image/photo/sketch to 3D), plugin-authoring (extensions the user installs; a tool never installs code), stock-and-fixtures.
- **Specialist agents** (`packages/ai/src/nikcli/agents.ts`; nikcli's `Agent` roster and `SUBAGENT_TOOLSETS` made to measure): the `cadcam` agent delegates with `agent_task {description, prompt, agent?, background?}` (nikcli's `task`; `subagent_type` and the host name `cadcam-editor` are accepted as aliases, unknown keys are dropped). Each specialist is a deny-by-default host agent with only the tools its job needs, a prompt of its own and a step budget: **researcher** (`cadcam-worker`, read-only: describe, check, list operations, parameters, machine, analyse G-code, libraries, memory, read-only version control; background by default), **editor** (`cadcam-editor`: the smallest change, `cad_modify/transform/group/delete`, `cad_editor`, `cad_check_design`), **modeler** (`cadcam-modeler`: new components with `cad_add_elements/entities`, `cad_import_drawing`, `cad_transform_entities` for copies, `cad_check_design`), **machinist** (`cadcam-machinist`: all `cam_*` tools, libraries, `actions_run`). All of them can read `vcs_status`, `vcs_diff`, `vcs_list_pull_requests`; none can start a change, commit or open a pull request (those stay with `cadcam`), delegate or set goals. A specialist that edits (`edits`) runs **in the parent's turn** (the call waits and returns its report) and **one at a time per project**; a read-only one returns a task id and wakes the parent with its report. The runtime-wide scheduler (`BackgroundTaskManager`, 4 active / 16 queued, scoped to `(projectId, parentSessionId)`) is unchanged and gained `wait()` (aborting the parent's call cancels the task), the exclusive editing rule and per-task `agent` / `edits` / `background`. The specialist runs in a child session created in **the host of the project that asked** (its tools act on that project's drawing), with the parent's model, and a transient provider failure is retried twice (`isTransientFailure`) before the task fails.
- **Specialists are visible and live.** Their tool calls are forwarded to the parent's stream (`event-mapper.ts`, `adoptChildSession`): `tool_call` / `tool_result` / `tool_progress` carry an optional `agent` and a call id prefixed with the child session id, so the editor, the CAM page and the transcript update while the specialist works exactly as for the main agent; text and reasoning of the child are not mixed into the parent's answer. `POST /api/ai/sessions/state` also returns `tasks` (id, agent, description, status, background, report), and the store polls it while a task is active and after a background report wakes the agent, then shows the agent's answer and re-syncs the editor (`watchTasks`). The chat shows the task list (`ai-tasks`), every tool call as an expandable row with its specialist, exact input and output (`ToolRow`), and facts for version control and workflows (branch, commit, pull request #, workflow status, a link to the project's version-control screen). The desktop no longer reports the sidecar's own tools (`agent_task*`, `vcs_*`, `actions_run`) as "not allowed".
- **Prompts** are written per role: the main prompt (units and tool-call hygiene, modelling, machining, workflow, agent behaviour, delegation briefs, version control, files, asking, style), one prompt per specialist (shared basics, method, boundaries, report format) and the `gcode` / `toolpath` / `cam` modes. They tell the agent to build in small steps (5 to 15 elements per call, one operation at a time end to end) because the user watches the model and the program appear. `tool-prompts.test.ts` checks the specialist prompts with the rest.
- **Honest limitations**: a specialist does not see the conversation (the brief is its whole context); nested delegation, session continuation (`session_id`) and a per-call model override are not implemented; background reports show in the chat through polling (about 2 s), not a push; the specialist's own text is not streamed. `bunx tsc` clean for `packages/ai`, `packages/api`, `apps/sidecar`, `apps/desktop`; `agents.test.ts` (roster, manager, tool, mapper), `specialists-host.test.ts` (real host, fake model: routing to the right project, restricted tools, forwarded events, retry) and `ai-specialists.test.ts` (chat UI).
- **Precision**: elements take `tolerance` (mm) and are meshed to it (`segmentsFor` in core); the drawing's tolerance is the default of round elements, of the generator's `tolerance` and of the verification.

### Continuous-agent contract (WP8 follow-up)

See **Specialist agents** above: `BackgroundToolsRunner` (`background-tools-runner.ts`) creates the child session (`session.create({title, parentID})`), prompts it with the specialist's agent, waits for the host's `prompt` result, removes the session, and for background tasks wakes the parent with `session-prompt.promptAsync({delivery: "queue"})`. Cancelled tasks do not wake the parent, cancellation keeps the slot until the runner stops, `dispose()` cancels everything, and `cancelForParent(parentSessionId)` is called when the parent session is removed.

### Uploaded mesh interoperability

The desktop attachment boundary parses STL (binary/ASCII), OBJ and PLY using its installed Three.js loaders and packages actual triangles as bounded `cadcamfun-mesh` JSON. `cad_import_drawing` accepts this representation through the existing project attachment store and existing add-elements persistence/editor pipeline. Mesh geometry is validated before persistence; original geometry is preserved and never advertised as a recovered parametric feature history. Explicit scale converts source units to mm. Unsupported binary/native formats fail explicitly rather than being decoded as text.

`cam_suggest_parameters.candidates` evaluates up to four explicit cutter/material/operation parameter combinations without saving operations. Candidate tools and materials are resolved through access-controlled libraries; missing ids fail the candidate. Actual generators and stock verification calculate each result. Reports retain source properties, requested cutting family, geometry-derived suggestions, runtime statistics and removal/collision findings. Comparisons require configured stock and never invent material suitability, measured cutting forces or recovered catalogue data.

Active-drawing correlation: every project tool resolves the desktop snapshot's `drawingId` only within the user's accessible project before falling back to the newest drawing. Tool arguments and session metadata cannot override the bound project. Vision correlates the exact stored geometry with the captured scene hash; captured renderer matrices include scene origin offsets, distinct from nominal element placement and machine work offsets.

### Full neutral CAD file decoder

The existing desktop attachment pipeline may decode STEP/IGES/BREP with the pinned official `occt-import-js` OpenCascade WASM module, without a conversion server. STEP/IGES output is converted to mm, source B-rep face ranges and assembly names are kept as import metadata, and the output feeds the existing validated mesh import. This extends the existing prismatic STEP fallback rather than replacing parametric modeling, renderer, database or CAM. BREP has no declared unit conversion; its source units remain explicit. Unsupported proprietary formats remain errors. WASM must be bundled locally; no CDN or execution of uploaded code.
# Explicit workspace scope and stock fidelity

AI tools must reject an inaccessible explicit project ID instead of falling back to another document. Only the `default` workspace sentinel may resolve or create the local user's workspace. A stock configured by the agent remains authoritative in the desktop CAM request, including its position and top face; linking a reference element must not silently replace the configured dimensions. Mesh import metadata records the source-to-mm scale separately from source tessellation settings.

CAM vision hashes the actual rendered toolpaths (tool IDs and complete moves, independent of display names) and compares them with the selected saved operation. Unsaved/unassociated previews remain visibly identified as such; a selected operation with mismatching program geometry fails capture rather than providing stale evidence.

## Fusion 360 modelling through the assistant (2026-10-13)

The assistant builds any form with measures, parametrically, from the feature history (`packages/core/src/cad/history.ts`); there is no second modeller.

| Fusion 360 | History | Notes |
| --- | --- | --- |
| Rectangle, circle, polygon, ellipse, slot, any outline | `sketch.shapes` (`sketch-shapes.ts`) | Every measure is a number or an expression of the parameters; shapes are fully constrained; a shape's points are named `<id>.p0` ... |
| Fit-point spline, control-point spline, Bezier | `shapes` of kind `curve` (`spline`, `nurbs`, `bezier`) | Sampled from the evaluated control points at every rebuild; open = sweep path, `chord` = closed profile for extrude/revolve |
| Extrude, Revolve, Sweep, Loft, Hole, Pattern, Mirror, Shell, Fillet/Chamfer, Draft | `extrude`, `revolve`, `sweep`, `loft`, `hole`, `pattern`, `mirror`, `shell`, `fillet`, `taper` | Existing |
| Box, cylinder, sphere, torus, gear, ... | `primitive` | The 3D element catalogue with parametric `params`, `at`, `rotation`, and an `operation` so a catalogue solid can also cut |
| Coil | `coil` | Helical sweep of a round or square wire; pitch must exceed the wire diameter |
| Move/Copy, Scale, Split Body, Combine | `move`, `scale`, `split`, `combine` | Act on whole bodies by id |
| Rib / Web | `rib` | Every open line chain of a sketch is thickened (butt ends, mitred corners) and stands `depth` mm along the sketch normal; united by default |
| Sheet metal base flange | `sheet` | One open chain, `thickness` on `side`, INSIDE `bendRadius` on every bend (the drawn line's own radius follows from the side), extruded `width`; `flatPatterns` in the report gives the developed length (K-factor 0.44) |
| Thread (modelled) | `thread` | ISO metric basic profile as real helical geometry, external rod or internal tapped-hole cutter; exact pitch, crest and root widths. `cut: true` cuts an external thread into the shaft already there; `axis` x / y runs it sideways |
| Text (emboss / engrave) | `text` | Single-stroke font solidified with a stroke width; union raises it, subtract cuts it in |
| Construct plane (offset, at angle, through 3 points) and Sketch on face | `plane` (`from.kind`: `offset`, `angle`, `points`, `face`), then `plane: <id>` on a sketch, hole or text | A face plane sits at the face centre with u = world X projected on the face, so a top face reads like XY; it is looked up again on every rebuild, so what is drawn on it follows the face. Holes on a work plane are skipped by the DFM check (it measures in XY/YZ/ZX) |
| Draft of a face of any body | `draft` | `name` tilts that face; a missing name is an error. Without it, the face is tilted about its hinge (face plane meets the neutral plane); the wedge between the old and new plane is added below and removed above the neutral plane |
| Joint (rigid, revolute, slider) | `mate` | Face to face: normals opposed, centres together, `offset` gap, `spin` (revolute), `slide` [u, v] along the target face (slider / planar), `limits` that turn a pose beyond them into an error, and an interference warning with the overlap volume |
| Press Pull (flat and curved faces) | `pushpull` | `name` (for example `plate.top`) moves that face; a missing name is an error. Without it, the planar face nearest a point (with its holes) moves along its normal; a mesh has no face objects, so it is rebuilt from coplanar triangles |

### Solid check in the parametric report (2026-10-13)

`parametricReport` (the result of `cad` `parametric_validate` and of every parametric create/edit) lists `solids`: for each body, welded first, whether it is a closed solid, its shells, its through holes (genus) and its triangle count, from `meshTopology` in the core. The `modeler` prompt makes the agent check that every body is `closedSolid: true` and that `throughHoles` equals the holes it meant to make before going on, so a Boolean that went wrong or a hole that did not cut through is caught by the assistant, not by the CAM or the printer.

### CAM coverage of every element (2026-10-13)

Every element type the assistant can create reaches the CAM. `packages/ai/test/cam-elements.test.ts` walks the whole element catalogue and requires each type to be one of: a solid with a mesh, a flat shape or curve with an outline, a container machined through its parts, or `text3d` (no solid: the part model reports it as skipped, and the toolpath engraves it along the strokes of `cad/stroke-font.ts`, a single-stroke font; characters without a glyph are left out and named in the G-code).

- Solids: `cam/model/element-mesh.ts` now builds sweep, loft, spring, bolt, screw, nut, washer, wall, floor, window, door, column (plain and styled), roof (gable and flat) and stair from the geometry the editor draws, standing on Z as the catalogue says. A spring whose turns touch is refused rather than meshed with a surface that crosses itself. A wall's openings are markers in the editor and are not cut. The stair is a solid flight (every step filled down to the base).
- Containers: `cam/model/model.ts` flattens components and groups (children placed relative to the parent) before building the part model; `isSolidElement` counts a container when something inside it is a solid.
- Outlines: `elementOutline` samples spline (Catmull-Rom), Bezier and NURBS (B-spline) elements, follows an extrusion's circle or profile, and gives bolts, washers, nuts, springs and columns their round or hex footprint. `outlineToolpath` cuts along the curve (open curves on the centre line, in plan) or round the closed profile with the tool offset.
- Tests: `packages/core/src/cam/model/element-cam.test.ts` (volume against the analytic value, ray pairing as the dexel model needs it, mesh bounds against the bounds the generator places by, toolpaths that leave the bounding rectangle).
