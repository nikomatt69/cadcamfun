# 55 — Evidence, performance, scale and qualification (the parity scorecard)

Status: specified 2026-10-24 (not built). Part of [spec 39](39-professional-parity-master-plan.md). Closes gate 1 of
[spec 12](12-professional-cad-cam.md) ("recorded corpus evidence"). Owner: WP1 + WP2 (shared test infrastructure under
`packages/core/test/corpus/` and `scripts/`), release process WP10. **This spec is built first (Wave A): without it no other
spec can say how far it got.**

## 1. Problem

Every spec says "parity is not claimed". The repository has thousands of unit tests (core: 2 427 tests over 164 files at the
2026-10-22 baseline; 170 test files under `packages/core` today) but no shared answer to: *how often does the kernel handle a real
part?*, *how fast?*, *how big?*, *on which machine does the G-code run?* This spec defines the corpus, the benchmarks, the scale
targets, the qualification record and the scorecard that turns those into levels.

## 2. Corpus (`packages/core/test/corpus/`)

- **Manifest** `corpus.json`: per entry `{ id, source, licence, hash, kind: "step"|"iges"|"stl"|"dxf"|"history"|"nc", expected }`
  where `expected` holds the oracle values (volume, area, centroid, face / edge counts, bounding box, colours, PMI count,
  tolerances of the comparison). Files with restrictive licences are **not committed**: the manifest stores a download
  instruction and the hash, and the runner skips what is absent, reporting the skip.
- **Sets**: (a) own parametric parts (`recipes.ts`, liquid mixer, rack-and-pinion gripper of the harness goal), committed;
  (b) public STEP / IGES (NIST MBE PMI CTC/FTC, open-licence sample parts and assemblies); (c) generated stress parts
  (fuzz seeds of spec 42, a fully rounded box, a 58-turn thread, 200-hole plate); (d) CAM reference parts with annotated
  features (spec 54 R1) and NC goldens.
- **Runner** `bun run corpus` → `data/corpus-report.json` and a table: per entry `pass | refused(reason) | wrong(diff) | slow`.
  `wrong` fails CI; `refused` is allowed only with a reason that exists in the refusal registry; `slow` is a budget breach.

## 3. Benchmarks and budgets

- `bun run bench` runs a fixed list (Boolean on corpus pairs, fillet / shell, history rebuild exact, STEP read/write, tessellation,
  drawing generation, CAM plans for reference parts, verification replay, assembly interference screening) and writes
  `data/bench.json` with median and p95 over N runs plus the machine fingerprint (CPU, load average). Machine load from other
  sessions doubles times: the runner records the load and refuses to compare when it differs by more than a factor set in the
  config; timings are judged against the **budget** in `bench.config.json`, not absolute history.
- **Gate:** a change that worsens a benchmark's median by > 20 % against its budget needs a recorded justification in the commit.
- Existing time gates stay (`gates.test.ts` 15 s budget; history-brep suite split in two halves to stay below 118 s).

## 4. Scale targets (declared, measured by the benchmarks; all are targets until measured)

| Target | Value |
|---|---|
| Single part, 5 000 faces: exact rebuild of a 60-feature history | ≤ 20 s |
| Boolean of two 2 000-face bodies | ≤ 5 s |
| STEP read of a 50 MB / 100 k-face file | ≤ 60 s, memory ≤ 2 GB |
| Assembly: 500 occurrences of 50 definitions open (spec 46 A7) | first frame ≤ 3 s |
| CAM: 3-axis finishing of a 100 k-triangle part | ≤ 60 s plan, verify ≤ 120 s |
| Viewport | ≥ 30 fps with 1 M triangles on the reference GPU (spec 37) |
| FEA 50 k DOF static | ≤ 10 s (spec 48) |

## 5. The scorecard

`specs/assets/parity-scorecard.md` is generated by `bun run scorecard` from tests tagged with a capability id
(`@parity(<area>.<capability>)` in the test title or a sidecar `parity.json` listing the tests and corpus subsets that prove it).
Capabilities are the rows of the gap tables of specs 40–54 (e.g. `blend.rolling-ball`, `boolean.coincident`, `cam.swarf`,
`turn.threading`, `exchange.step-pmi`). Columns: **Fusion 360, SolidWorks, Creo, hyperMILL** — each with the capability's
reference expectation (written from public vendor documentation with the URL and date, not from memory; an unreachable page is
recorded as such) — and **this project's level**:

| Level | Meaning |
|---|---|
| 0 absent | no code |
| 1 partial | works on named cases, refusals not exhaustive |
| 2 functional | works on the declared domain; typed refusals outside it |
| 3 robust | passes the corpus subset (§2) with 0 wrong results, within budget |
| 4 qualified | 3 plus an independent oracle and, for CAM, a qualification record (§6) |

A row can move up only when its gate tests pass in CI. **The word "parity" may be used in a document only for a row at level 3 or
higher, naming the row.** The README and specs must link to the generated scorecard instead of restating levels.

## 6. Qualification of CAM output on real machines

- **Record** `qualification/<machine>-<controller>-<date>.json`: machine and controller model + software version, post id and
  version, fixture description, test program id, the air-cut result (collision-free, motion matches the simulation: observed vs
  simulated cycle time and axis positions at checkpoints), the test-cut result (material, tool, measured part dimensions vs
  model with the instrument and uncertainty, surface finish if measured), the operator and date, photos/CMM report hash.
- **Rules**: a post is `qualified` for a controller only with an air-cut and a test cut on a named machine; a release level
  `qualified` is granted per (post, machine, operation family), never globally; the record is referenced by the release claim
  and checked into `qualification/` (data only, no secrets).
- **Program of work (decision D7):** the owner names the machines available (the project already lists KERN Micro HD, Haas,
  Mazak/Okuma classes by preset) and the first target; until a record exists, turning stays `preview` and milling stays at the
  `verified-model` level described in spec 29.
- **Tolerances measured, not inferred:** the measured error budget of a (post, machine) pair replaces the generic budget of
  spec 53 V5 for that pair.

## 7. Independent oracles

- OpenCascade reader as used by `apps/desktop/test/cad-iges.test.ts` for STEP / IGES (volumes within 0.1 %).
- Analytic closed forms (Green's formula for profile areas, frustum / torus / sphere sector volumes).
- Sampled truth: grid / Monte Carlo volumes at ≤ 0.2 %.
- Simulation oracles: analytic removal volumes for simple pockets and spheres; seeded fault injection (spec 53 V2).
- For FEA: closed-form beam, Lamé and stress-concentration references (spec 48).

## 9. Honest limits

- Vendor reference expectations are *capability descriptions from public documentation*, not comparative performance or
  quality benchmarks.
- A corpus is a sample: passing it bounds the failure rate, it does not prove the absence of failures.

## 10. Order

a machine is named, E8 last.
